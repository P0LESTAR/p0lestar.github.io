## Objective 4: Identify Credential Theft

공격자가 AWS 자격증명을 어떻게 사용했는지 추적하는 문제다.

우선 CloudTrail 로그에서 `ListBuckets` 이벤트를 찾는다.

```bash
> jq '.Records[] | select(.eventName=="ListBuckets")' *.json

{
  "userIdentity": {
    "type": "AssumedRole",
    "arn": "arn:aws:sts::653711331788:assumed-role/level3/d190d14a-2404-45d6-9113-4eda22d7f2c7",
    "accessKeyId": "ASIAZQNB3KHGNXWXBSJS"
  },
  "eventName": "ListBuckets",
  "sourceIPAddress": "104.102.221.250"
}
```

### ListBuckets 이벤트 분석

**공격자가 AWS 계정에 접근하면 가장 먼저 수행하는 행동 중 하나가 현재 계정의 S3 버킷을 확인하는 것이다.** (aws s3 ls)

CloudTrail에서는 위 명령이 **ListBuckets** 이벤트로 기록된다.

따라서 침해사고 분석 시 ListBuckets 이벤트는 공격자의 초기 정찰 행위를 확인하는 좋은 단서가 된다.

---

### 어떤 권한이 사용되었는가?

로그를 보면 `userIdentity.type` 값이 `AssumedRole`이다.

```json
{
  "type": "AssumedRole",
  "arn": "arn:aws:sts::653711331788:assumed-role/level3/..."
}
```

IAM User가 아니라 STS를 통해 발급된 임시 자격증명이 사용되었고, ARN을 보면 level3 Role이 사용된 것을 확인할 수 있다.

---

### level3 Role 확인

```bash
aws iam get-role --role-name level3

...
{
  "AssumeRolePolicyDocument": {
    "Statement": [
      {
        "Principal": {
          "Service": "ecs-tasks.amazonaws.com"
        }
      }
    ]
  }
}
```

해당 Role은 ECS Task만 사용할 수 있도록 설정되어 있다.

정상적인 경우라면 **ECS Task -> AssumeRole(level3) -> AWS API 호출** 같은 흐름이 되어야 한다.



---

### 수상한 IP 주소

CloudTrail 로그를 보면 API 호출 IP는 **104.102.221.250** 다. 해당 IP는 AWS 소유 IP가 아니다. (힌트보고 알았다)

만약 ECS Task가 정상적으로 Role을 사용했다면 AWS 내부 네트워크 또는 AWS에서 사용하는 IP 대역이 나타나야 한다.
하지만 실제 로그는 외부 인터넷 IP에서 API를 호출하고 있다.

---

### 요약

CloudTrail 로그에서 `ListBuckets` 이벤트를 확인한 결과 `level3` Role이 사용되었다.

하지만 해당 Role은 ECS Task만 사용할 수 있도록 설정되어 있었으며, 실제 API 호출은 AWS 외부 IP에서 발생했다.

따라서 ECS 환경에서 발급된 임시 자격증명이 탈취되었고, 공격자가 이를 이용하여 AWS API를 호출한 것으로 판단할 수 있다.
